Muse's Lab: Generating Hands-On Learning Games at Runtime for Seated Mixed Reality and Walkable Virtual Worlds

Pramod Thebe

pthebe.sfsu@gmail.com    Technical report, November 18, 2026

Abstract

Generative user interfaces (GenUI), in which a language model writes the interface for each request, have mostly been studied on flat screens. Extended reality (XR) adds constraints a web page never meets: content must be within reach of the hands, readable at depth, placed relative to a body that may be sitting at a desk or walking through a world, and checked without a person wearing the headset. We present Muse's Lab, a WebXR system for Meta Quest in which an agent turns a spoken or typed question (“how do kites fly?”) into a playable learning game while the learner waits. Every game is one JavaScript module that the host mounts either as a toy on a detected desk in passthrough mixed reality or as a walkable world in full VR. Before it reaches the headset, every module passes static rules, a strict dry run and a geometric layout checker for reach, occlusion, start clearance and label size. Across more than 500 generations scored by one independent judge, we find that (i) letting the model write code beats the declarative A2UI format and fixed templates on quality (paired differences +0.42 and +0.70 on a five-point scale, 95% confidence intervals above zero), and code was the only format to pass every check on the first try; (ii) the system matters more than the model: our rendering and verification rules raised five models from four providers by +0.12 to +0.53 and shrank the spread between them from 0.41 to 0.08; (iii) a one-call lesson tier produces a working hands-on scene in a median 27.6 s at tied-best quality, and streaming parallel builders show content about twice as soon at a measurable quality cost; (iv) for full games built by a sandboxed coding agent in about 13 minutes, the model and the pipeline dominate, and the layout checker removes every blocking or unreachable layout. In an emulator, 283 of 330 hand interactions landed across 65 lessons, and on a Quest 3 we found and removed a leak of 13.5 MB per game.

Keywords: generative UI, extended reality, mixed reality, WebXR, LLM agents, code generation, educational games, spatial layout, evaluation.

Introduction

Children learn a great deal by handling things: tilting a kite into the wind, stacking stones against a current, folding paper until a plane glides. Mixed reality (MR) and virtual reality (VR) headsets can put such experiences in front of anyone, but each one is still built by hand. A lesson library answers the questions its authors anticipated, and a curious learner's next question is usually not among them.

Generative UI offers another route: let a model write the experience for the request at hand. On a screen this is now routine, and a failure is cheap: a misaligned button, an overlong label. In a headset the failures are physical. A panel can open in the learner's face; a button can sit behind a wall or two metres overhead; a world can spawn the player inside a rock; a label can be unreadable at arm's length. The learner is also in one of two very different situations. Seated at a desk with the room visible through passthrough, they want a toy within reach on the table. Standing in a cleared space with the room hidden, they can walk through a world built at full scale. A system that writes XR experiences at runtime has to serve both, and it has to know, without a human tester, whether what it wrote can actually be used.

This paper describes and measures such a system. Muse's Lab runs in the Quest browser on Meta's Immersive Web SDK (IWSDK) [13]. A learner asks a question by voice or text; Muse, the app's tutor, turns it into a game whose rules teach the idea (a kite climbs when lift exceeds its weight; water pushes harder the deeper it gets). We ask four questions:

  • RQ1, format. Should the model write code, a declarative UI description (A2UI [5]), or only fill in hand-built templates?
  • RQ2, model or system. How much do the choice of model and the design of the surrounding system each contribute?
  • RQ3, speed. How fast can a usable spatial experience appear, and does splitting the work across parallel builders help?
  • RQ4, games. When an agent builds a complete game over many steps, which parts of the pipeline make the result better?

We also report what the hands could actually do with generated content in an emulator, and two reliability problems that only appeared on the headset.

Contributions.

  • A two-tier runtime GenUI architecture for XR: a one-call lesson tier that answers in seconds and an agentic game tier that builds a full game in minutes, both producing one module contract that runs as a seated MR desk toy or as a walkable VR world (Section 3).
  • Verification without a person in the headset: static rules, a strict dry run with readable-text bounds, and a geometric layout checker for reach, occlusion, start clearance, hold size and angular label size, whose findings are returned to the model to repair (Sections 3.4, 5.5 and 5.6).
  • To our knowledge, the first controlled comparison of open, declarative and controlled GenUI on one XR runtime with the same checks, probes and judge (Section 5.1), and a five-model, four-provider benchmark with interaction-aware scoring (Section 5.2).
  • Measurements of one-shot and streamed parallel generation (Section 5.3), a 35-game factor study of an agent pipeline (Section 5.6), and headset reliability findings (Section 5.7). All prompts, records and the analysis script are in the project repository.

What is and is not new. Runtime generation of XR scenes with language models is not new [1, 2], nor is an AI tutor that shows 3D models on Quest [7]. What we have not found elsewhere is the combination studied here: an end-user system that writes a complete, rule-based learning game for an arbitrary request at runtime; runs the same generated module either seated in mixed reality or walking in full VR; checks its spatial ergonomics automatically before the learner sees it; and is evaluated across output formats, models and pipeline factors with the same hand probes and judge. We state this as a gap in the work we found (Section 2), not as a claim of priority.

Related work

Runtime language models for XR. LLMR [1] builds and edits interactive mixed-reality scenes in Unity with a set of cooperating model modules (scene understanding, planning, self-debugging) and reports a four times lower error rate than plain GPT-4. XR Blocks [2, 3] is an open WebXR framework designed for code generation, with a semantic model of the user, the world and the UI; Vibe Coding XR [2] prompts it from inside the headset and introduces VCXR60, a 60-prompt benchmark whose pass criterion is a run without console errors in headless Chromium, measured on one model family. Google's three-live [6] runs agent-written three.js code in a sandbox and declares XR behaviour as traits (grab, billboard, anchor), the same split between generated content and host-owned input that we use. Our work differs in its target (complete learning games, not scenes), in serving both seated MR and walkable VR from one module, and in scoring interactions and layout rather than only the absence of errors.

Declarative and controlled GenUI. LLMER [4] has the model emit JSON against schemas instead of code and argues that this avoids script errors and saves tokens. A2UI [5] is an open format for agent-generated UI with custom component catalogs. Controlled GenUI, where the model only selects and fills pre-built components, is the common production pattern. These approaches had not been compared with open code on the same XR runtime and tasks; Section 5.1 does so.

Learning and tutoring in XR. CuriosityXR [7], on the Meta store since 2023, answers spoken questions and places 3D models the learner can grab and take apart; from its listing we could not determine whether it generates content or retrieves it from a library. Reality Copilot [8] is a voice assistant on Quest 3 that generates single 3D objects on a server. Embodied AR instructors such as ARIA [19] adapt dialogue rather than build interactive content. To our knowledge none writes the interactive lesson itself for the learner's request.

3D content through code, and evaluation. SceneCraft [9] and LL3M [10] generate Blender code for scenes and assets with critic loops; P3D-Bench [11] finds multi-part assemblies much harder than single parts, and WorldBench [12] shows that judges reading only code over-credit 3D worlds compared with judges that run them. We score rendered scenes with a vision-language judge [17] and add emulated-hand probes, and our layout checker measures the built scene rather than the code. Finally, Meta's IWSDK 1.0 [13] ships agent tooling (an MCP server that drives an emulated headset) for developers at build time; we use the same runtime headlessly inside the coding agent's sandbox, at the learner's request time.

System

Overview

Figure 1 shows the two paths from a request to the headset. The lesson tier makes one model call with a fixed system prompt and returns a module, which a gate checks; a failure is sent back with the gate's error, up to two times. The game tier first designs the game in one call (its title, the idea it teaches, its rules and controls, and whether it plays on the desk or as a world) and draws two planning pictures. A coding agent then builds the game in a sandbox, a grader compares the result with the plan and may send it back once, and the same gate checks it before the headset loads it. The app opens with a shelf of ready-made games so that a learner always has something to play while a new one is built.

One module contract for every game

Every lesson and game is a single ES module whose default export is build(api) (Listing 1). The host passes three.js, a kit of helpers for panels and 3D labels, sound, and an entity-component-system (ECS) world from EliCS [15], on which IWSDK itself is built. Generated code never reads raw XR input. It marks objects with traits (grabbable, pressable) and the host wires them to IWSDK's grab and pointer systems for hands and controllers. This split matters: grabbing worked in every setup of our game study (Section 5.6) because the host owns it. Panels are flat UI built with @pmndrs/uikit [16]. The game tier writes its logic as ECS components and systems (Listing 2), which gives the agent a fixed vocabulary for state and behaviour.

The teaching is in the rules. In the kite game the agent wrote a small flight model (Listing 2): the apparent wind va combines the wind at the kite with its own motion along the line, lift and drag grow with va2, and the kite climbs along its line only while lift exceeds its weight:

va=w2+(ωℓcosφ)2,L=kva2(1−0.1|b|),φ¨∝(L−mg)cosφ−Dsinφ

where w is the wind speed, ω the kite's sideways angular speed, ℓ the line length, φ the elevation, b the bank from the handle and mg = 0.65 kg × 9.81 m/s² = 6.38 N. The constant k = 0.319 plays the role of ½ρCLA. The panel shows the live wind and lift, so the learner sees the number change as they steer. Nothing in our prompts specified this model; the agent derived it from the design's teaching goal. We did not verify the physics of every generated game, and the judge scores only visible correctness (Section 6).

Two bodies, one module: desk mode and world mode

A module states where it plays by returning mode: 'desk' (the default) or mode: 'world'. The design step chooses the mode from the request: “a windy hilltop I can walk around” becomes a world, “fold a paper plane” stays on the desk. Figure 2 shows both placements.

Desk mode (seated, mixed reality). Passthrough stays on, and the host looks for a horizontal surface among the planes the headset detected. Let h be the head position, f the horizontal gaze direction and d* = 0.55 m the comfortable reach. For each candidate plane the host takes the point p on it nearest to h + d*f, kept 0.12 m inside its edges, and chooses

p⋆=argminp∈𝒫|‖p−h‖xz−d⋆|+λ1[ℓ(p)∉{table, desk}]

with λ = 0.15 m, where ℓ(p) is the plane's semantic label and the feasible set 𝒫 keeps points 0.15 to 0.9 m below the eyes, at least 0.15 m above the floor, 0.3 to 0.9 m away horizontally and within 50° of the gaze. Floors, beds, sofas, chairs and benches are skipped: in testing, a learner sitting on a bed had every game placed in their lap. The game's largest side is scaled to 0.9 m (0.5 m for a lesson), and its panel stands beside it.

World mode (standing, full VR). A world is written in the same desk units, around an origin where the player stands with −z ahead, and shown s = 12 times bigger:

xworld=sx+oplayer,s=12,

so a kit sized for the desk also builds a walkable hillside, and one checker can measure both. The host draws the sky (day, dawn, dusk, night or overcast), fogs the horizon between 30 and 88 m so the world has no hard edge, and enables IWSDK locomotion (slide, teleport and snap turn) on the meshes the game marks walkable. The game's panel stands 0.9 m ahead of the player, a little to the left and below the eyes. Closing a world stops locomotion and puts the player back where they were, so the room lines up with passthrough again.

Verification before the headset

Every module passes three stages, and any failure becomes a message to the model naming what to change.

Static rules. The module is parsed (acorn) and rejected if it references network, storage, timers, dynamic code or host globals (fetch, eval, Function, document, localStorage, setTimeout and 25 others), including names assembled from string literals. Panel text is checked against the 104 glyphs of the headset's font atlas; any other character would render as an empty box, and the error names each character with its plain-text replacement.

Strict dry run. The module runs as a strict-mode module in a separate process against a stub host with a simulated hand, so runtime errors, empty scenes and broken handlers surface before the headset. Panel text must be readable at seated distance: with a panel wui metres wide whose root is wroot pixels wide, text of f pixels is

htext=wuifwroot≥1.1cm,

panels may turn at most 0.4 rad away from the learner, and grabbable objects closer than 4 cm to each other are flagged, since a pinch cannot choose between them.

Layout checker. The built scene is measured from where the player is. At the desk, a hand target is hidden when no ray from three eye positions (centre and 0.2 m either side) reaches it, and text that faces away is flagged. In a world, the checker samples the first view on a grid Ω of rays, yaw from −35° to 35° and pitch from −45° to 10° in 5° steps, and computes the share of rays blocked within 1.5 m:

β=1|Ω|∑ω∈Ω1[thit(ω)<1.5m],note ifβ>0.1,must fix ifβ>0.2.

It also requires a clear circle of 0.42 m around the player's feet from knee to head height, hand targets between 0.24 and 1.92 m above the ground (with a comfortable band of 0.48 to 1.56 m), carried objects no wider than 0.48 m in their middle dimension, and labels of a sensible angular size. A label of height h read from distance d subtends

θ=2arctanh2d,tag: note above 8°, must fix above 14°; sign: 16° and 26°.

For reference, a name tag on a desk game subtends about 3°. Findings are either must fix (the module is returned) or notes (passed to the model as advice). Appendix B lists every rule.

The game tier's agent

The coder is a Deep Agents [14] agent on LangGraph, run in a Modal sandbox [20] per game with the network blocked and no secrets. The sandbox holds the gate, the headset app and a set of skills: folders of instructions, references, scripts and worked examples for the learning-game rules, the ECS kit, eight visual looks (for example soft clay, low poly, ink and toon), sound, and play-testing. A starter script writes game.js, the only file the agent edits, beside the shared kits. The agent reads the two planning pictures, writes the game, runs the gate and the learning-game rules with a check script, and opens the module in the real IWSDK runtime, run headless, to take screenshots from the player's position. When it stops, a grader compares the game with the plan against a rubric and may send it back once. A run is capped at 40 model calls, 80 tool calls, 15 minutes and a per-attempt budget. Sounds come from a library of 30 prepared effects and ambiences before any are generated.

Evaluation method

Requests. The lesson tier was tuned on ten development requests and evaluated on twelve held-out ones (for example “a glowing button that changes colour each time I press it”, “build a molecule: hydrogen and oxygen atoms I can grab”), each generated twice per arm, and on twelve harder applications (a pendulum lab, a chess puzzle, a three-step form). The 3D study used twelve objects with four to seven named parts. The game study used four requests: a forest river dam, a kite hill and a desert canyon as worlds, and a paper plane on the desk.

Probes. Each scene that passed the gate was mounted in the IWSDK emulator (Quest 3 profile, seated, emulated right hand), which records whether it mounted without runtime errors, whether a grabbable object was held and followed the hand, whether a 3D press fired its handler, and whether up to three panel buttons worked.

Judge. One vision-language model that generated none of the scored content (Claude Opus 5.5) scored each mounted scene from the request and one screenshot from the seated learner's view, without being told which model or format produced it. It gave four scores from 1 to 5: fidelity to the request, clarity of text and layout, visible correctness, and hands-on (whether it is clear what to grab or press). The full rubric is in Appendix A. A scene s's quality is

Q(s)={14∑k∈Krk(s)if s passed the gate,1otherwise,

with K the four criteria. Scoring failures as 1 means an arm's mean counts what it failed to deliver instead of averaging only its successes. The game study used a separate blind judging pass on identical opening views with shuffled file names and four criteria (fits the request, clear in five seconds, looks, shows the idea), totalled out of 20.

Statistics. Arms are compared on the same requests. For arms A and B over requests R, with Q̄(r) a request's quality averaged over its repetitions,

ΔAB=1|R|∑r∈R(Q¯A(r)−Q¯B(r)),

with a 95% percentile bootstrap interval from 10,000 resamples of R with replacement [18] and an exact two-sided sign test on the requests that differ. Times are wall-clock from request to accepted module. Costs are at each provider's list price; Meta's models had no public price at the time and are left blank. docs/paper/analysis.py recomputes every number in this paper from the stored records.

Results

RQ1: code, a declarative format, or templates?

We built three versions of the lesson tier that differ only in what the model writes. In A (open) it writes the module's code. In C (declarative) it writes A2UI v1.0 messages against a spatial catalog we defined (3D Scene, Shape, Group, Arrow, Orbit, Spin, plus A2UI's panels, buttons and data bindings), which, as far as we know, makes it the first A2UI renderer for WebXR with hand input. In D (controlled) it picks one of five hand-built lesson components (explorable object, orbit system, process cycle, bar chart, sorting game) and fills in its data. C and D compile to the same kind of module A writes, so the host, gate, probes and judge are identical. Table 1 and Figure 3 give the results.

Open code was both the most reliable and the best. Code passed every check on the first try with both models (48 of 48), while A2UI needed repairs in about a third of runs (17 and 15 of 24 first try) and Ember failed 2 of 24 outright. On quality, code beat A2UI on 10 of 12 requests with Sonnet (ΔAC = +0.42, CI [0.16, 0.68], p = 0.039) and 11 of 12 with Ember (+0.70 [0.34, 1.18], p = 0.006), and beat templates on every request it did not tie (+1.28 [0.98, 1.53] and +1.32 [0.98, 1.64]). This runs against the argument that structured output avoids script errors [4]: with current models, the errors moved into the structured format instead (misnested JSON, unbound data paths, panel text too small).

Control buys speed and costs fit. Templates never failed, were three to four times faster (10.7 s and 8.6 s median) and about four times cheaper than code with the same model ($0.017 against $0.070 per Sonnet lesson), but scored 3.0. Their fidelity was 2.3 against 4.5 to 4.6 for code: a component built in advance rarely fits a request it was not built for, such as a habit tracker or a colour-changing button. Grabbing, which templates expose only where a component has it, worked in 6 of 9 probes against 30 of 30 for code. A2UI sits between the two on every measure.

Two caveats apply. Version A's prompt had been refined over four earlier runs on the development requests, while C and D are first versions. And building C surfaced bugs in our own renderer (panel rotations ignored, unhelpful error messages, one-number rotations rejected) that we fixed before the measured runs; a less mature declarative runtime would compare worse still.

RQ2: the model or the system?

We ran five models from four providers on the code version: Claude Sonnet 5.5, Muse Spark 1.3, Muse Ember 1.0 at maximum reasoning, Kimi K3.1 Pro and DeepSeek V4.1 Flash. The first round used our original system. Reading the judge's notes showed that most lost points were the system's, not the models': 13 of Ember's 24 scenes, 18 of Kimi's and 8 of Sonnet's used characters outside the panel font (CO₂ subscripts, emoji) that rendered as empty boxes; panels without a fixed width shrank their text; panels turned away from the learner. We added the glyph rule, the text-height bound of Equation 4, the panel-turn limit and a larger output budget, and re-ran every model on the same requests (Table 2, Figure 4).

The system mattered more than the model. The changes raised every model, by +0.12 (Sonnet) to +0.53 (Ember), and shrank the spread between the best and worst from 0.41 to 0.08. Afterwards all five scored 4.22 to 4.30, and no model differed from the best (Kimi, 4.30) by a paired interval that excluded zero; the largest gap, DeepSeek's, was +0.08 [−0.14, 0.29]. Ember's progression shows where the points came from: from 3.77 to 4.04 after the glyph rule and to 4.30 after the readable-panel rules, with clarity rising from 2.71 to 3.67 and first-try success from 21 to 24 of 24, at an unchanged median time (27 to 29 s). With quality tied, the choice of model reduces to speed (Ember, 27.6 s median), price (DeepSeek, $0.010 per scene) and how often its buttons worked (DeepSeek 95%, Sonnet 92%, Muse Spark 71%).

Complexity separates the models again. On twelve harder applications (Table 3), all 60 succeeded and ran without errors, but the spread grew to 0.38 and clarity fell for everyone (3.0 to 3.4): more panels mean more crowding. Sonnet, Kimi and Ember led. Ember stayed within 0.08 of the best at four times Sonnet's speed (46.8 s against 187.5 s) with the most reliable buttons (91%). Figure 5 shows both runs on one speed–quality plane.

RQ3: how fast can a hands-on scene appear?

The lesson tier with Ember delivers a checked, working scene in a median 27.6 s (interquartile range 21 to 35 s), and templates in under 11 s at a large cost in fit. To show something sooner, we built a streaming version of C: a fast planner splits the lesson into two to six parts, each with its place, the names other parts may use and the shared data; placeholders appear as soon as the plan exists; one builder per part runs in parallel with the same model, checks and repair budget as one-shot generation; and each part streams to the headset the moment it passes. Table 4 and Figure 6 compare it with one-shot C on the same requests.

Parallel builders show content about twice as soon and cost quality. The first real part arrived after 18.5 s instead of 39.8 s (Sonnet) and 14.0 s instead of 29.1 s (Ember). The whole lesson took 26 to 37% longer, and quality fell by 0.37 [0.17, 0.58] for Sonnet; Ember's drop of 0.46 has a wide interval [−0.18, 1.16] because it also failed more lessons outright (4 of 24 against 2), since a lesson needs every part to pass. The judge's notes point to integration: parts built apart fit together less well than one design. We kept one-shot code for the lesson tier and the shelf of ready-made games for an instant start; streaming remains available where showing progress matters more than polish. Our own latency targets (placeholders in 1 s, content in 8 s, a full lesson in 30 s) were met only by the last, and only by one-shot code.

3D objects with named parts

Games need objects whose parts can be named, highlighted and grabbed. We compared three ways to build twelve such objects with Ember: three.js code inside the module (P1), CadQuery, a CAD kernel (P2), and an agent driving Blender through MCP (P3), each judged on the same four-view render (Table 5). All three produced every required part as a separate named node. No pipeline was clearly better on quality: P1 − P2 = +0.33 [−0.08, 0.75] and P1 − P3 = +0.17 [−0.17, 0.50]. P1 was the fastest and cheapest and needs no server, since its geometry is part of the module. A critic loop that keeps the best of up to three rounds added a small, reliable gain (+0.17 over all 72 jobs, CI [0.07, 0.26]; the delivered model was worse than the first round in only 1 of 72), while reference images did not help (−0.11 [−0.31, 0.08]) and added about 17 s. The game tier therefore builds its own geometry in code.

What the hands could do

We mounted 65 lessons in the emulator: two hand-written fixtures, 35 lessons from saved courses (23 code only and 12 built around a generated 3D model), four library lessons, and the A2UI and template lessons from RQ1. For each, an emulated hand tried every interaction the lesson offered. An interaction counted only when the app saw it land: a generated handler ran, a held object followed the hand at least 5 cm, or a model's parts spread at least 1 cm. Figure 7 shows the matrix.

Every interaction worked on the hand-written fixtures, so the failures in generated content point at the host, not the gestures. Two host bugs explained most of them, each confirmed with a minimal test lesson: an object that was both grabbable and pressable ignored point-and-pinch presses (9 of the 12 failed presses had the ray reach such an object first), and the host moved pressable parts out of a grabbable model, leaving the model empty. We fixed both: parts now stay in their model and are pressed through it, and a near-grab handle ignores fingertip touches so that reaching in to pinch does not knock the object away. Two-hand scale and rotate are not implemented.

RQ4: what made the agent's games good?

The game tier went through 19 iterations while we built it. To see which changes mattered, we took 35 games that already existed from 11 setups, all answering the same four requests, and scored them the same way on the same day: a blind judge on identical opening views, today's layout checker, and a hands probe. Each setup changes one or a few things against another, so pairs of setups on the same requests show what a change did (Table 6, Figure 8). All 35 games ran without runtime errors; the median build took 13.1 minutes.

The model was the largest single factor. With the pipeline fixed, replacing GPT-6.1 Sol by DeepSeek V4.1 Flash lowered the score by 3.75 points out of 20 (worse on 3 of 4 requests), and the DeepSeek games took longer (17.4 against 13.2 minutes). Sonnet 5.5, run through a general coding agent without our design step, play-test or planning pictures, scored 2 points lower; that is not a clean model comparison, since the pipeline differed.

The pipeline came next. One round of cleanup (a much smaller editable file, the title shown by the host instead of a sign in the scene, a corrected cost meter) improved all three requests it was tested on (+2.67). Writing game logic as ECS systems improved both of its pairs (+2.5, a small sample) and made builds faster, and it has been the default since.

The layout checker is a floor, not a ceiling. Its third version removed every must-fix (four to zero: nothing blocking the start, nothing out of reach, nothing huge in the learner's face) at no cost to the score (+0.67). The first two versions did not help (−1.67 and −0.67), and their misses led to the rules in Section 3.4.

Planning pictures set the composition. On the first view, games built with planning pictures (P) were level with those without (S): −0.5, better on two requests and worse on two. The coder copies the plan picture closely, good or bad. When the plan picture crowded the view, so did the game. On the headset, however, the author played the games and rated P the best of all setups for physics, interaction and assets, which an opening screenshot cannot show. P is the deployed configuration, and its four games are the app's ready-made examples.

On the headset

Two problems appeared only on a real Quest 3, and both are general lessons for runtime GenUI in a long-running XR session (Table 7).

Every game stayed in memory. After many games the headset slowed down. On the device, page memory grew by (571 − 409)/12 ≈ 13.5 MB per game. Scene objects and GPU textures were released correctly; JavaScript kept every old game alive through three library behaviours. The UI library disposed of only the panel's root, so every other element stayed in the layout engine's global handle table, which led through a click handler back to the whole game. The ECS kept every component class in a global registry, and each game makes fresh ones. And destroyed entities kept their component data. The host now disposes of panel elements children-first, removes a game's component classes from the registry and clears destroyed entities' data; memory stays flat over 16 games.

Scrolling stopped after a few pixels. IWSDK's pointer reuses one event object for every move, and the UI library marks that object once it has scrolled. Because the mark was never cleared, a list scrolled about 5 px and stopped for both hands and controllers. Clearing the mark every frame (Listing 4) restored it, and the dashboard also scrolls with the thumbstick.

Discussion

Why code wins in XR. A spatial lesson's value is mostly in its behaviour: what moves, what responds to the hand, what number changes. Code expresses that directly, and current models write it reliably once the host takes care of input and the gate returns precise errors. Declarative formats move the same mistakes into nested JSON, and templates cannot express a request they were not built for. We expect the gap to narrow as declarative catalogs grow, but the reliability argument for them did not hold here.

Put the effort into the system. On simple requests the system's rules were worth more than any choice among five frontier models, and the rules that mattered were spatial and concrete: glyphs the headset can draw, text tall enough to read at 0.55 m, panels that face the learner, objects a pinch can tell apart, worlds whose start is clear and whose targets are within reach. These rules transfer to any model, so the model can then be chosen for speed, price or availability. The deployed app uses GPT-6.1 Sol for the game tier and is moving to a Muse model, a choice our results suggest is safe on simple requests and needs re-measuring on complex ones.

Fast and rich are different tiers. No single path delivered both a full game and a sub-minute answer. A one-call lesson arrives in under half a minute; a game that teaches through its rules takes about 13 minutes of agent work. Streaming halves the wait for first content but costs quality. The product therefore combines an instant shelf, fast lessons and slower games, and tells the learner when a game will be ready.

One module, two bodies. Building worlds in desk units and scaling them by a constant let one kit, one gate and one checker serve both seated MR and walkable VR. The cost is that scale errors are magnified twelve-fold, which is why the world rules exist: an innocent 4 cm label on the desk becomes a 48 cm sign in the player's face.

Limitations

  • One judge. All quality scores come from one vision-language model, from the same company as one of the models tested (Sonnet). It saw one screenshot, not the running scene, so it cannot judge physics or game flow. A pilot with four judges in run 1 found very different curves (one family's judge averaged 4.7, another 3.8), which is why we report one consistent judge rather than a mixture.
  • Small samples for games. The factor study has two to four games per setup and one picture each; differences under about 2 of 20 points are within noise. The strongest evidence for the deployed setup is one person's headset play.
  • No learning outcomes. We measured whether experiences work and fit the request, not whether children learn from them. A study with learners, comparing generated games with hand-built ones, is the necessary next step.
  • Emulator, not headset. Interaction probes ran in IWSDK's emulator with one emulated hand. Fingertip pokes on panels were the least repeatable probe. The headset findings in Section 5.7 come from one device.
  • Records. Muse Ember's original-system records were replaced by its improved run; its original mean (3.77) is taken from our run log. The interaction matrix's raw probe files were kept locally; its table is copied from our records. Model versions change quickly; every result is dated November 12 to 18, 2026.
  • Correctness of generated science. The judge rated visible correctness high (4.75 and 4.88 for code), but nobody verified every generated physics model. Games for children need review of the ideas they teach, for example by a second model checking the rules against the design's teaching goal.

Safety. Generated code runs in the learner's browser, so the static rules block network, storage, timers and dynamic code, and the coding agent runs in a sandbox without network access or secrets. These rules limit what a module can reach; they do not judge whether its content is appropriate for children, which needs its own review.

Conclusion

Muse's Lab shows that a model can write complete hands-on learning experiences for XR at the learner's request, and that the same module can be a toy on a real desk or a world to walk through. The measurements point to three practical conclusions: let the model write code and give it a host that owns input; invest in spatial verification, because it lifts every model and lets the model be chosen on speed and price; and separate fast lessons from rich games instead of forcing one path to do both. The open questions are the ones we did not measure: whether children learn from these games, and how to verify the science inside them automatically.

Appendix A. The judge's rubric (lesson tier)

The judge received the request, one screenshot of the mounted scene from a seated learner's view, and this instruction (verbatim):

You are judging generative UI for a mixed-reality headset. An AI was asked to build an interactive spatial
component from the request below; the screenshot shows the result as seen by a seated user.

Ignore everything that is not the generated component:
- the living room (a simulated stand-in for the user's real room seen through passthrough),
- emulator controls: the top-right "Runtime / Editor" bar, the "Remote Control Active" badge,
  white outline hands and any controller or hand panels in the corners.

Score the generated component from 1 (very poor) to 5 (excellent) on:
- fidelity: does it show what was requested, with nothing important missing?
- clarity: is the text legible and the layout tidy (no overlaps, nothing clipped or hidden)?
- correctness: are the visible facts, labels and numbers correct? (5 if nothing factual is shown)
- handsOn: is it clear what the user can grab or press, and does it invite interaction?

Reply with only a JSON object: {"fidelity": n, "clarity": n, "correctness": n, "handsOn": n, "notes": "one sentence"}
